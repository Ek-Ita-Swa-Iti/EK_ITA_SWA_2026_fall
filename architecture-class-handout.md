# A Self-Maintaining Wiki — A Software Architecture Case Study

## What is it?

A directory of markdown files that gets written and kept up to date by an LLM (e.g. Claude, ChatGPT). You give the LLM source documents — papers, articles, code, course materials — and it builds and maintains a structured wiki about them. When the sources change, the LLM updates the wiki to match.

There's no server, no database, no user interface. The "application" is just a folder.

## The three layers

```
raw/        <-- the source material (read-only)
wiki/       <-- the LLM writes and updates this
CLAUDE.md   <-- the rulebook the LLM follows
```

Three deliberate roles:

1. **`raw/`** — the source of truth. The LLM is **never** allowed to write here. Whatever you put in becomes the input.
2. **`wiki/`** — the LLM's working area. Every page in here was generated by the LLM. You read it; the LLM writes it.
3. **`CLAUDE.md`** — a plain-English file that tells the LLM how the wiki should be organized: what pages look like, what filenames to use, what to do when a new source arrives, what rules to follow.

This separation is the **architecture**. There's almost nothing else to the system — and yet, with these three layers in place, you can build something genuinely useful.

## Architectural ideas you can read out of this

### 1. Boundaries matter more than components

There are only three "components" (folders/files), but the **rules about what can write where** are the load-bearing part. If the LLM is allowed to edit `raw/`, you lose your source of truth. If the human has to edit `wiki/` by hand, the system collapses into a normal manual wiki nobody maintains.

> **Boundary**: a rule about who is allowed to do what across two parts of a system. Boundaries are usually more important than the parts themselves.

### 2. A "contract" can be written in English

In conventional software, the contract between two parts is usually code (a function signature, a type, an API spec). Here, the contract is `CLAUDE.md` — written in plain English and interpreted by an LLM.

> **Contract**: an agreement that says "if you give me X, I'll give you Y." It tells two parts of a system how to talk to each other.

This is unusual. It has trade-offs:
- ✅ Easy to read and change.
- ✅ The author and the LLM can co-evolve it.
- ❌ Ambiguous. Two different LLMs might interpret it differently. A human can't *prove* the wiki is correct.

Discussion-worthy: when is an English contract good enough? When isn't it?

### 3. A small convention can carry the whole system

Inside `CLAUDE.md` there's a rule that every concept on a topic page must be tagged with one of:

- `introduces` — first time the topic teaches this concept
- `reinforces` — the topic uses the concept again
- `assumes` — the topic depends on the concept but doesn't teach it

These three words make it possible to ask the wiki questions like *"which concepts are used but never taught?"* or *"if I move week 9 earlier, what breaks?"* Drop the convention and the wiki becomes unstructured notes.

The lesson: **architecture is often a tiny rule that everything else relies on.** Lose the rule and the structure collapses, even if the folders look the same.

### 4. Change detection by remembering "where we left off"

Sources change over time. Re-reading every source from scratch on every change would be wasteful. Instead, the wiki remembers the last version it processed (using git's commit IDs) and asks git: *"what changed since then?"*

Only the changed files are re-processed.

This is a very general pattern — the same idea shows up in build systems (rebuild only what changed), database backups (incremental backups), and version control (diffs). Worth recognizing once you've seen it here.

### 5. The whole thing is just files

No database. No server. No API. The state is on disk. You can read every part of it with a text editor. Git gives you version history and rollback for free.

> **Side effect:** you can copy the whole system by copying the folder. You can back it up by committing it. You can inspect any layer just by opening a file.

This is a deliberate architectural choice — and a strong one. Discuss: what does this design buy you? What does it cost?

## Discussion questions

1. Where is "the architecture" in this system? Point at the file or rule that holds it together.
2. What happens if you remove the LLM? Does the architecture still exist, or did the LLM *create* it?
3. Compare this to a system you've seen with a database and a web server. What's missing here? What's gained?
4. The contract (`CLAUDE.md`) is written in English. Find one place where an English contract is risky — where you'd want code instead.
5. If two people share one of these wikis and both ask their LLMs to update it at the same time, what could go wrong?
